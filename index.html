Paper reading notes · Agent engineering · October 2026

The best model is not enough.

I started with a common question: Which model is best for agents? This paper shows why that question is incomplete. The result depends on the model, the harness around it, and the task they face together.

Why this paper mattered to me

I have spent enough years in BI to know that a report is not trustworthy just because the visual looks good. Source quality, semantic grain, refresh logic, security and validation decide whether the number can be trusted. I had not been applying the same discipline to agents. I was still giving too much weight to the model name. This paper corrected that.

01

The paper in six minutes

I changed the question before looking at the answer.

Question I would have asked earlier Which model has the highest agent benchmark score?
→
Question I would ask now Which model-harness configuration works best on my task, at my cost and risk level?
1

Model rankings can reverse

On Terminal-Bench 4, Claude beat GPT inside OpenHands. Inside PI, GPT beat Claude by a much larger margin. The model order was not stable.

2

The best harness depends on the task

For four of the five models, the winning harness changed when the benchmark changed. A working pair is not automatically portable.

3

The vendor's own harness is not automatically best

Claude Code led Claude on two benchmarks but lost to OpenHands on Terminal-Bench 4. Codex never produced GPT's highest score in this study.

4

More spend does not guarantee more capability

The same model could cost several times more in another harness while scoring lower. Cost belongs inside the evaluation, not after it.

5

Error feedback changes recovery

Models initiated almost all repairs. The decisive difference was often whether the harness returned a timeout, argument error or failure in a usable form.

6

Self-verification can be confidently wrong

An agent saying “verified” is not independent evidence. It may be testing against a criterion it invented, changed or misunderstood.

A

One-sentence explanation

A capable brain can still fail when the surrounding system gives it unclear tools, hides failures, lets commands hang, forgets progress or accepts weak proof of completion.

02

A model is not an agent

The harness is the operating system around the model.

The paper uses harness for everything that turns a language model into an acting system: tool definitions, context handling, retries, timeouts, permissions, continuation rules and stopping rules. The model reasons. The harness decides how that reasoning touches the world.

1TaskWhat must be done
→
2ModelReasons and chooses an action
→
3HarnessValidates and executes the call
→
4Tool / environmentReturns output or failure
Feedback returns through the harness

Model

The language model producing reasoning, text and tool calls. In this study: Claude Opus 5, GPT-6 Astra, GLM-5.3, Kimi K3 and DeepSeek V4 Pro.

Harness

The runtime system around the model. It exposes tools, maintains context, handles errors, decides retries and determines when work stops.

Task

The actual job and environment. A harness that helps on one class of work can hurt on another.

Evaluator

The external judge that scores the final result. It must not be confused with the agent's own self-check.

What exactly can a harness control?
Tool interfaceNames, schemas, required arguments and error messages
ContextWhat is kept, compressed, cached or removed
ExecutionTimeouts, sandboxing, permissions and shell behavior
ContinuationWhether interrupted work resumes and with what prompt
StoppingTurn limits, stuck detection and completion markers
Verification supportChecks, acceptance criteria and evidence shown to the model

Important:

This is not a controlled laboratory experiment where every timeout, tool, context window and turn limit is identical. The paper compares complete working configurations. That is useful for deployment decisions, but weaker for claiming that one isolated harness feature caused a score difference.

04

What the results say

Six findings I would carry into an agent architecture review.

01

Ranking instability

The same two models can swap places when only the harness changes.

On Terminal-Bench 4, Claude scored 57.14% in OpenHands while GPT scored 49.21%. Claude led by 7.94 points. In PI, Claude scored 30.16% and GPT scored 60.32%. GPT led by 30.16 points.

The observed Claude-versus-GPT gap moved by 38.09 percentage points between those two harnesses.
What I take from this

A model leaderboard cannot tell me how that model will rank inside my runtime. Replacing a model in an existing agent is a system change, not a drop-in API change.

02

Task-dependent fit

For four of five models, the winning harness changed across benchmarks.

Claude, GPT, GLM and DeepSeek each had different observed winners as the task collection changed. Kimi was the exception: openJiuwen produced its best score on all three benchmarks.

Claude Claude Code → Claude Code → OpenHands GPT openJiuwen → PI → PI GLM openJiuwen → OpenHands → DSH Kimi openJiuwen → openJiuwen → openJiuwen DeepSeek openJiuwen → OpenHands → DSH
What I take from this

“Best harness” is not a property of the harness alone. It is an empirical result for a model and workload. I should evaluate on representative tasks, not generic demos.

03

Native is not a guarantee

The vendor's own agent can win, lose or sit in the middle.

Claude Code was Claude's best harness on TUA-Bench and ALE-CLI, but OpenHands led it by 7.94 points on Terminal-Bench 4. For GPT, Codex was beaten by openJiuwen on TUA-Bench and by PI on ALE-CLI and Terminal-Bench 4.

What I take from this

Vendor alignment may improve integration, but I would not turn it into an architecture rule. Native provenance is evidence to test, not a decision shortcut.

04

Cost-performance fit

A more expensive run can be substantially worse.

On Terminal-Bench 4, GPT with PI scored 60.32% at about $4.66 per task. GPT with DSH scored 52.38% at about $19.94 per task. The lower-scoring configuration cost more than four times as much.

What I take from this

Model price is not agent cost. Tool-loop length, uncached context, retries, compaction and auxiliary calls can dominate. I need score, latency and cost from the same evaluation run.

05

Persistent fit can exist

Kimi and openJiuwen were a stable favourable pair in this study.

openJiuwen led Kimi's strongest alternative by 5.61, 6.91 and 11.11 points across TUA-Bench, ALE-CLI and Terminal-Bench 4. The advantage remained after removing the three largest positive task gaps.

But the advantage was not uniform by domain. On ALE-CLI, openJiuwen led PI strongly in life sciences and business/finance, while trailing in computing/math.

What I take from this

A repeatable pairing is meaningful, but I should still inspect domain slices. An aggregate win can hide a local loss in the workload I actually care about.

06

Process matters

The harness changes calls, context reuse and the shape of failure.

For the same model, harnesses produced large differences in model-call counts and uncached input tokens. openJiuwen served 94–99% of its input tokens from cache in the reported configurations, versus 49–77% for the others.

The paper also found that trajectory length alone did not identify efficiency or correctness. A longer path could be the one that fixed the real defect.

What I take from this

I should trace the whole execution: calls, tokens, cache, tool errors, retries, wall time, final evidence and stop reason. A single pass rate hides too much.

07

Why the fit changes

The trajectories explain more than the leaderboard.

The paper inspected matched runs: the same model doing the same task under different harnesses. These examples show where runtime design changes the outcome.

192actionable failure-signal events coded in matched Terminal-Bench pairs
180responses initiated by the model rather than the harness
69%of responses were diagnosis or a targeted patch
116 / 133diagnosis-or-patch responses resolved the signal

What the model usually supplied

Diagnosis and repair

Once a useful failure signal arrived, the model often identified the problem and corrected it. This suggests that many failures were not a simple lack of reasoning capability.

What the harness had to supply

A usable signal and a safe next step

A timeout must return as a timeout. A malformed tool call must return a structured argument error. Interrupted work needs a continuation policy. Human-required steps need an escalation path.

08

My application of the paper

I would evaluate the agent configuration, not approve the model in isolation.

My interpretation, not a paper result

The examples in this section apply the paper's logic to enterprise BI, data engineering and agent operations. They were not part of the published benchmarks.

SQL / BI agent

Same model, different trust boundary

A model may generate the same SQL in two systems. One harness runs it with read-only credentials, row limits, query timeout, schema context and result checks. Another gives broad access and returns raw database errors. These are not the same agent.

  • Test semantic correctness, grain and KPI definitions.
  • Return normalized SQL errors to the model.
  • Block writes by policy, not by prompt.
  • Validate the answer against known queries and edge cases.
ADF / workflow agent

Retry logic can create or prevent damage

A “helpful” retry can duplicate a file load, resend a notification or rerun a non-idempotent step. The model is only one part of the failure behavior.

  • Classify retryable and non-retryable errors.
  • Use idempotency keys and run-level state.
  • Set bounded retries, timeouts and stop reasons.
  • Escalate ambiguous production actions.
Power BI change agent

“The file saved” is not acceptance

An agent can edit a measure and confirm that the model opens. That does not prove the KPI still reconciles, RLS still works, refresh succeeds or dependent reports are unaffected.

  • Define independent acceptance tests before the run.
  • Compare totals, slices, lineage and performance.
  • Preserve a rollback artifact.
  • Require evidence, not a confident completion message.

My decision rule

I would not promote the configuration with the highest average score. I would promote the configuration that meets the minimum quality and safety gates, then gives the best cost-latency trade-off on representative work.

09

What the paper does not prove

Useful result, limited claim.

One counted run per task

The study did not estimate run-to-run variance. A different run could change a close comparison.

Defaults were not uniform

Tools, context management, turn limits and execution budgets varied by harness. The results compare configurations, not isolated components.

Three fixed task collections

The findings are strong evidence for these settings, not proof that the same ranking holds for every enterprise workload.

Matched case studies were selective

The trajectory analysis gives mechanisms and examples, but it is not a complete causal decomposition of all 6,204 runs.

Proposed fixes were not tested here

The training-data and harness-design recommendations are evidence-grounded proposals, not validated interventions in this paper.

No tuned enterprise stack

The study intentionally did not add custom skills, memory, MCP servers or task-specific prompts. A production system may behave differently.

Claims I would not make after reading this

  • “openJiuwen is the best harness.”
  • “Kimi is better than the other models.”
  • “Vendor-native agents are poor.”
  • “More context or more turns always improves results.”
  • “The harness caused every observed score difference.”

The defensible claim is narrower: the observed value of a model or harness depends materially on the configuration and task, so they should be evaluated together.

10

My final position

The model is a component. The agent is the governed system.

Before this paper

I treated harness choice mainly as an implementation preference around the model.

After this paper

I treat model-harness fit as an evaluated architecture decision with its own quality, cost, security and operational evidence.

  1. 01

    Benchmark the complete configuration on representative tasks.

  2. 02

    Keep quality, cost, latency and safety in the same scorecard.

  3. 03

    Trace failures far enough to distinguish model limits from runtime limits.

  4. 04

    Return tool and execution failures as structured feedback.

  5. 05

    Use bounded timeouts and explicit stop states.

  6. 06

    Do not accept the agent's own test as independent proof.

  7. 07

    Define acceptance criteria before execution where possible.

  8. 08

    Keep a human escalation path for genuinely human-only steps.

  9. 09

    Re-evaluate when the model, harness, tools or workload changes.

  10. 10

    Prefer evidence over model reputation or vendor convenience.

Deployment confidence Representative tasks × external verification × runtime controls × observed cost Not model name alone.
